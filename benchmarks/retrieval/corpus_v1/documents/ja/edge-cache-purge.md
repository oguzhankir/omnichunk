# 端点キャッシュの削除要求表

| Scope | Rule | Condition |
| --- | --- | --- |
| 経路の正規化 | 削除対象の経路は配信時と同じ規則で正規化する。ただし正規化の結果が別の契約領域へ移る指定は拒否し、利用者の経路を管理用経路へ拡張しない。 | 削除の照合と配信の照合を同じ契約境界に保つ。 |
| クエリ文字列 | キャッシュキーに含めたクエリ項目だけを削除の照合に使う。配信で無視する追跡項目を削除キーへ足さず、同じオブジェクトへの要求を分散させない。 | 配信キーと削除キーの不一致を避ける。 |
| ワイルドカード | 利用者が所有する公開接頭辞の内部だけに適用する。契約全体を表す管理用ワイルドカードへ自動変換せず、所有範囲を越える要求は拒否する。 | 広すぎる削除による他の配信物の失効を防ぐ。 |
| 再試行識別子 | 同じ削除要求の再送は同じ操作識別子を使う。削除範囲が変わった場合は新しい識別子を要求し、過去の成功結果を異なる範囲へ流用しない。 | 通信再試行と新しい削除操作を区別する。 |
| 受付と完了 | 制御面の受付は全端点での削除完了を意味しない。応答には受付状態を示し、完了は端点ごとの確認を集計した別の状態として公開する。 | 利用者が早すぎる再公開を判断しないようにする。 |
| 応答の鮮度 | 削除状況の応答には観測時刻を添える。古い集計結果を最新の完了確認として扱わず、観測が途絶えた端点は不明のまま残して成功率から隠さない。 | 遅れた状態通知を完了の根拠にしない。 |
| 原本の再取得 | 削除後の再取得は原本側の公開許可を改めて確認する。キャッシュに以前存在したという理由で非公開となった原本を再配信しない。 | 失効した公開許可がキャッシュ再生成で復活することを防ぐ。 |
| 連続する削除 | 同じ経路への新しい削除には新しい世代番号を割り当てる。遅れて届いた旧完了通知が新しい削除を完了にしないよう、端点の確認には世代番号を照合する。 | 繰り返し操作でも完了通知の順序逆転を安全に扱う。 |
| 配信停止 | 緊急の配信停止はキャッシュ削除の完了を待たず公開許可を取り消す。削除操作は残った複製の回収として継続し、公開禁止の判断を遅延した端点の応答へ依存させない。 | 緊急停止と複製回収の責務を分ける。 |
| 監査記録 | 削除の対象経路は監査用の制限領域に保存する。一般の運用指標には操作識別子と件数だけを出し、利用者が指定した非公開経路を指標ラベルにしない。 | 監視データから非公開コンテンツの所在が漏れることを防ぐ。 |
